This website and its pipeline

vithu.cloud is a static site with no web server. The files sit in an S3 bucket, CloudFront serves them over HTTPS from the edge location nearest to you, and a pipeline deploys every change.

Built with
S3, CloudFront, GitHub Actions, IAM OIDC, CloudFormation, AWS CLI, hand-written HTML, CSS and JavaScript

How this page reached you

No web server sits behind this site. The details below are read from the response your browser just received.

  1. Your browserAsks for vithu.cloud over HTTPS
  2. DNSPoints the domain at the nearest CloudFront edge
  3. CloudFrontEdge location serves the cached page
  4. Amazon S3Origin bucket holding the site files, encrypted at rest

How a visit works

  1. Your browser looks up vithu.cloud and is pointed at a CloudFront edge location.
  2. CloudFront answers over HTTPS. If the page is in its cache, it replies straight away.
  3. If it is not, CloudFront fetches the file from the S3 bucket, returns it and keeps a copy.
  4. The panel at the top of this page reads the x-amz-cf-pop and x-cache response headers to show which edge served you and whether the cache was used.

How a deploy works

  1. The repository has a GitHub Actions workflow that runs when the site folder changes on the main branch.
  2. GitHub gives the job a signed token that says which repository and branch it is running for.
  3. AWS checks the token against an IAM role that trusts only the main branch of this one repository, then hands back credentials that last an hour.
  4. The job runs deploy.sh, which uploads the files with cache headers and tells CloudFront to drop its cached copies.

The trust policy

Condition:
  StringEquals:
    token.actions.githubusercontent.com:aud: sts.amazonaws.com
    # only the main branch of this one repository may use the role
    token.actions.githubusercontent.com:sub: !Sub "repo:${GitHubOwner}/${GitHubRepo}:ref:refs/heads/main"

The role itself can list and write objects in the site bucket and create CloudFront invalidations. It can do nothing else in the account.

Why it is built this way

  • A static site has no server to patch and nothing to scale.
  • CloudFront keeps the page fast wherever the visitor is, and it handles the TLS certificate.
  • OIDC means there is no long-lived access key to leak or rotate.
  • The site has no framework and no build step, so the whole thing is a handful of files that load quickly.

What I would add next

  • The bucket, distribution and DNS records defined as code alongside the role
  • A CloudFront response headers policy for HSTS and a content security policy
  • A preview deployment for pull requests

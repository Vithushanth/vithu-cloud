Serverless web application

A web application where every layer is managed by AWS. It scales on its own, and it costs nothing while nobody is using it.

Built with
API Gateway, Lambda (Python 3.12), DynamoDB, S3, CloudFront, Route 53, IAM, CloudWatch, AWS SAM
View the code on GitHub

How it works

  1. The browser requests the site. CloudFront serves the static frontend from an S3 bucket, with Route 53 handling DNS.
  2. The frontend calls the REST API on API Gateway. GET /items and POST /items each map to their own Lambda function.
  3. get_items.py scans the table and returns the items as JSON. put_item.py gives each new item a UUID and writes it.
  4. DynamoDB stores the data on on-demand capacity, so there is nothing to size in advance.
  5. Both functions log to CloudWatch, and errors return a clean 500 response instead of a stack trace.

Why I built it

This is the standard serverless pattern, and I wanted to understand it end to end. Building it showed me how API Gateway maps routes to Lambda integrations and how CloudFront caching behaves in front of an S3 origin.

What I learned

  • How to scope an IAM execution role so a function can touch only the table it needs. The read function gets a read-only policy, and the write function gets a write-only one.
  • How API Gateway turns an HTTP request into a Lambda event, and what the function has to return for the response to be valid.
  • Why CORS headers matter when the frontend and the API live on different domains.

Least privilege in the SAM template

GetItemsFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: get_items.handler
    CodeUri: src/
    Policies:
      # read-only on this one table
      - DynamoDBReadPolicy:
          TableName: !Ref ItemsTable
    Events:
      GetItems:
        Type: Api
        Properties:
          Path: /items
          Method: get

The SAM template creates the API, both functions, the table and the frontend bucket. CloudFront and Route 53 sit in front of the bucket and are set up separately.

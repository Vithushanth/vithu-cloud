Short explanations of the AWS ideas behind my projects. Writing them down is how I check that I understand them.

Why OIDC beats stored access keys

A pipeline needs permission to deploy. The old way is to create an IAM user, generate an access key and paste it into the pipeline's secrets. That key works from anywhere, for anyone who gets hold of it, until somebody remembers to rotate it.

With OIDC there is no key. GitHub gives each job a signed token saying which repository and branch it is running for. An IAM role trusts tokens from one repository and one branch, and AWS swaps the token for credentials that expire within the hour.

Nothing long-lived is stored, so there is nothing to leak and nothing to rotate. The trust policy is also a precise statement of who may deploy.

What makes a subnet public

A subnet is public when its route table has a route to an internet gateway. Nothing else decides it. The name, the address range and the instances inside make no difference.

In my VPC, the public subnet is associated with a route table that sends 0.0.0.0/0 to the internet gateway. The private subnet uses the VPC's main route table, which only has the local route. An instance there cannot be reached from the internet and cannot reach out either.

An instance in a public subnet also needs a public IP address. A route with no public address still leaves it unreachable.

Security groups and network ACLs

Both filter traffic, but at different points and in different ways.

  • A security group protects an instance. It is stateful, so if a request is allowed in, the reply is allowed out automatically. It only has allow rules.
  • A network ACL protects a subnet. It is stateless, so inbound and outbound rules are checked separately and the reply needs its own rule. It can allow and deny, and rules are checked in number order.

I use security groups for nearly everything and keep network ACLs for broad rules, such as blocking an address range from a whole subnet.

Least privilege for a Lambda function

Every Lambda function runs with an IAM execution role. The role should allow exactly what the function does and nothing more.

My serverless app has two functions. The one that lists items has read access to one DynamoDB table. The one that adds items has write access to the same table. Neither can touch any other table, and the read function cannot write.

If a function is ever compromised or has a bug, the damage stops at what its role allows. Splitting permissions by function costs a few extra lines in the template.

The five parts of a CloudWatch alarm

Metric
What is measured. Mine is CPUUtilization for one EC2 instance.
Statistic
How the data points are combined. Mine is the average.
Period
The window each data point covers. Mine is 300 seconds.
Evaluation periods
How many periods in a row must breach before the alarm fires. Mine is 2.
Threshold
The value to compare against. Mine is 80%.

Together they read as: alert me when average CPU is above 80% for ten minutes. Two evaluation periods stop a single short spike from sending an email.

Why event-driven beats polling

A polling system checks for work on a timer. Most checks find nothing, and new work waits until the next check.

An event-driven system starts work when something happens. In my pipeline, the upload to S3 is the trigger. The file is processed within moments, and when nothing is uploaded, nothing runs and nothing is billed.

The thing that produces the event also does not need to know what consumes it. I could add a second function that reacts to the same uploads without changing the first.
